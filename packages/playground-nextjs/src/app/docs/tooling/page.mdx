`uxdsl init --multi` scaffolds a theme entry plus one component entry instead of one entry. `uxdsl generate-entry --src <dir> --out <file> --exclude <a,b>` rewrites the entry's `@import` list from the `.uxdsl` files under a directory. `uxdsl <command> --help` prints one command's options, `uxdsl --version` the installed version. An unknown command or flag fails before anything runs, with a suggestion.

## Two files, two jobs

The **build config**, `uxdsl.config.cjs` (or `.js`), says what to compile and where. The **theme file**, `uxdsl.theme.json` (or `uxdsl.theme.js`/`.cjs` exporting the object), holds the theme and nothing else; it is discovered next to the config, or in the working directory, by the CLI and by the PostCSS plugin, the Vite plugin and the Webpack loader alike. A config that carries `theme` or `breakpoints` is refused, naming where each belongs.

## Multiple entries and CSS Modules

The first entry defines every token in `:root`, once (`--include-theme`, the default). Every other entry — a component sheet, a CSS Module — compiles with `--no-include-theme` (or `includeTheme: false` in `builds`, or in the PostCSS plugin's options) and only consumes those tokens: no `:root`, so a CSS Modules loader accepts it, and nothing is repeated. This site does exactly that: every component's `.uxdsl` is a CSS Module compiled with `includeTheme: false`.

## Source maps

`--sourcemap` writes `<outFile>.map` and a `sourceMappingURL` comment, so devtools point at the `.uxdsl` line that produced a rule; `--sourcemap=inline` embeds the map. The Vite plugin and the Webpack loader pass their maps on to the next loader.

## Watch

`uxdsl build --watch` rebuilds when a source, an import, the config or the theme file changes. A broken edit is reported and the last good CSS stays on disk; the next valid save recovers. A session recorded by the capture script as it edited a file:

## The theme command: `--diff`, `--contrast`, `--strict-theme`

`uxdsl theme` prints the effective theme (no CSS written; it works from a theme file alone). `--diff` prints only what the theme file mentions, each leaf labeled `project` or `default`. `--contrast` runs the WCAG gate of [Accessibility](/docs/accessibility). `--strict-theme=<families>` fails when a named family was partly inherited — on `build` too; a scope is required.

## Editor support

- **VS Code:** the `uxdsl-vscode` extension highlights `.uxdsl` files and completes the token functions, breakpoints, directives, `@uxdsl theme;`, and the roles, tones and sizes of the base theme (not yet a project's own roles). It does not compile or validate; the build does.
- **The theme file:** `"$schema": "./node_modules/uxdsl/schema/theme.schema.json"` gives any JSON editor validation and completion of every family.
- **The config:** `init` writes `// @ts-check` and a JSDoc type on the config object, so the editor flags a mistyped key; nothing is loaded at build time for it.
