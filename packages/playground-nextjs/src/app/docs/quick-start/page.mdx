## 1. Install

```bash
npm i -D uxdsl
```

It needs Node.js 20.19 or later. `postcss` (`^8.4.31`) is a peer dependency, which npm 7 and later install for you.

## 2. Scaffold

```bash
npx uxdsl init
```

`init` writes four files and adds two scripts to `package.json`:

- `uxdsl.config.cjs`: what to compile and where, type-checked by your editor.
- `src/styles.uxdsl`: the file you edit.
- `src/uxdsl-entry.uxdsl`: the entry, a generated list of every `.uxdsl` file under `src`. Do not edit it: the watch regenerates it when a `.uxdsl` file is added or removed, and so does `npx uxdsl generate-entry`.
- `src/uxdsl-theme.uxdsl`: one line, `@uxdsl theme;`, which is where the theme's tokens are emitted. The entry loads it first.
- `uxdsl:build` and `uxdsl:watch`: the two commands of step 3, as scripts.

It writes no `uxdsl.theme.json`: the base theme is built in. What it prints in a new project:

## 3. Build, and keep building

```bash
npx uxdsl build --watch
```

Import the generated `src/uxdsl.css` once, from your root layout or app entry. A broken edit is reported with its `UXD_*` code and line; the last good CSS stays on disk until the next valid save.

## The file you edit, and what it becomes

`src/styles.uxdsl` starts with one rule. With no `uxdsl.theme.json` at all, it compiles to:

<WriteGet id="quick-start" />

<div className="doc-section">

That is the rule and the tokens it uses. The file on disk also carries the whole base theme: <CssSize run="init-build" />, about 5 KB gzipped, whatever the number of rules. Its first statement is an `@import` of Inter from Google Fonts, because the base theme's `fonts.google` lists it. A project that serves its own fonts, or whose Content Security Policy refuses that host, sets `"fonts": { "google": [] }` in its theme and no `@import` is emitted.

To change a token, add `uxdsl.theme.json` next to the config with only what you change — `{ "densities": { "3": "xs(space(2)) md(space(4))" } }` — and every `density(3)` follows. A running watch picks the file up when it is created, with no restart. The [Theme handler](/docs/theme#families) page lists every family, and lets you try a theme live before you write one.

## Your framework

The CLI works with any framework. Next.js, Vite and Webpack can also compile `.uxdsl` themselves, through the same pipeline.

<div className="doc-section">

Next.js with no CLI at all: the PostCSS plugin compiles every stylesheet of the app. A custom `postcss.config.js` replaces Next's default plugins, so it names them, then `uxdsl/postcss`, which takes no option for the theme:

```js
// postcss.config.js
module.exports = {
  plugins: {
    'next/dist/compiled/postcss-flexbugs-fixes': {},
    'next/dist/compiled/postcss-preset-env': {
      autoprefixer: { flexbox: 'no-2009' },
      stage: 3,
      features: { 'custom-properties': false },
    },
    'uxdsl/postcss': {},
  },
}
```

Write `@uxdsl theme;` once, at the top level of the one global stylesheet: the theme's `:root` is emitted there and nowhere else, so CSS Modules stay free of `:root`.

```css
/* app/globals.css, imported once from app/layout.tsx */
@uxdsl theme;

body { margin: 0; }
```

A misspelled, repeated or nested marker is `UXD_THEME_MARKER`. The plugin compiles one file at a time and has no end of build, so it cannot tell that no file wrote the marker: without it the page builds and the tokens resolve to nothing. The theme is the project's `uxdsl.theme.json`, discovered from the working directory.

</div>

```js
// vite.config.js
import { defineConfig } from 'vite'
import uxdsl from 'uxdsl/vite'

export default defineConfig({ plugins: [uxdsl()] })
```

```js
// main.js: a .uxdsl import is a CSS import, handled by Vite's own CSS pipeline (HMR, build extraction)
import './styles.uxdsl'
```

```css
/* styles.uxdsl, the global stylesheet: the theme is emitted here, once */
@uxdsl theme;
body { margin: 0; }
```

Vite 4 and later. The config is an ES module: in a project whose `package.json` has no `"type": "module"`, name it `vite.config.mjs`. The plugin discovers `uxdsl.theme.json` the way the CLI does; `import css from './panel.uxdsl?inline'` returns the compiled CSS as a string. Component modules leave the marker out and carry only their own rules. `vite build` warns `UXD_THEME_MARKER` once when no module reaches the marker while the CSS uses tokens, or when more than one emits the theme; the dev server reports only the second case.

Webpack 5. Use `MiniCssExtractPlugin.loader` instead of `style-loader` to extract a real `.css` file. Every `@import`-ed partial and the theme file are registered as dependencies, so watch mode sees them. Write `@uxdsl theme;` once, at the top of the global `.uxdsl` the app imports first, and leave it out of every other one: a second stylesheet that writes the marker emits the whole theme again. The loader warns `UXD_THEME_MARKER` once per compilation when no module, or more than one, emits the theme.
