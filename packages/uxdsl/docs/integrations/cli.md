# The `uxdsl` CLI

> The command-line interface for compiling **UXDSL** files into CSS.

Part of the [`uxdsl`](../../README.md) package (`npm i -D uxdsl`). Until 0.5.0-beta.6 this was the separate `uxdsl-cli` package; that name is deprecated and only re-exports `uxdsl`.

**[Visit the Official Documentation & Playground](https://uxdsl.io/)**

---

## Overview

The `uxdsl` command compiles `.uxdsl` files into a plain CSS file you import like any
other stylesheet — the way to use UXDSL with any framework or static-site
generator (Next.js included), or in a separate build step that keeps the
main bundler fast. It compiles through the shared
[`compile()`](compile.md) of the package root, the same pipeline
the [Vite plugin](vite.md) and the
[Webpack loader](webpack.md) use, so the same entry and theme
produce the same CSS everywhere.

## Installation

```bash
npm i -D uxdsl
npx uxdsl init
npm run uxdsl:build
```

`init` creates, never overwriting an existing file:

| File | What it is |
| --- | --- |
| `uxdsl.config.cjs` | the build config: what to compile and where (typed; your editor checks it) |
| `src/styles.uxdsl` | **the file you edit** |
| `src/uxdsl-entry.uxdsl` | the entry, generated by `generate-entry` from the `.uxdsl` files under `src/`; it loads `styles.uxdsl` with `@use`. Do not edit it |
| `postcss.config.js` | Next.js projects only, when absent: Next's own default PostCSS plugins plus `uxdsl/postcss` (a custom `postcss.config.js` replaces Next's defaults, so they are named explicitly) |

and adds `uxdsl:build` / `uxdsl:watch` scripts to `package.json` when they are
missing. Import the generated `src/uxdsl.css` once, from your root layout or
app entry. `src/styles.uxdsl` starts with one rule, so the first build is not
blank:

```css
.example {
  @ds-surface(contained);
  padding: density(3);
}
```

`npx uxdsl init --multi` scaffolds a `builds` array instead — a
theme entry (`src/theme.uxdsl`) plus one example component entry
(`src/panel-a.uxdsl`, `includeTheme: false`) — for a project that starts with
a theme and several CSS-Module panels.

## Commands

| Command | Does |
| --- | --- |
| `uxdsl init [--multi]` | First-run setup (above). `--multi`: a theme entry plus one component entry. |
| `uxdsl generate-entry [--src <dir>] [--out <file>] [--first <a,b>] [--exclude <a,b>]` | Rewrites the entry: one `@use` per `.uxdsl` file under `--src` (default `./src`, or the working directory when it has no `src/`), written by default to `uxdsl-entry.uxdsl` in that directory. Run it after adding or removing files (see [`generate-entry`](#generate-entry)). |
| `uxdsl build [options]` | Compiles the entry — or every entry in `builds` — to CSS, once. `--watch` keeps rebuilding. |
| `uxdsl theme [options]` | Prints the effective theme as JSON: the same discovery and resolution as `build`, no CSS written. |
| `uxdsl --help`, `uxdsl <command> --help` | The general help, or one command's options. Bare `uxdsl` prints the help; it does not build. |
| `uxdsl --version` | The installed `uxdsl` version (one package: the CLI, the compiler and the theme model are one install). |

An unknown command is one line with a hint. An unrecognized flag — a typo, or
a flag that belongs to another command — fails before anything runs, with a
suggestion when there is a close one, instead of being ignored.

### `build`

| Flag | Does |
| --- | --- |
| `--config <file>`, `-c` | The build config. Default: `uxdsl.config.cjs` or `uxdsl.config.js` in the current directory. |
| `--entry <file>`, `-e` / `--out <file>`, `-o` | Compile one file to one output without a config. |
| `--watch`, `-w` | Rebuild on changes (see [Watch mode](#watch-mode)). |
| `--include-theme` / `--no-include-theme` | Emit (default) or skip the global `:root` token definitions. Overrides `includeTheme` in the config. Accepted forms: bare, `--no-…`, `=true`, `=false`. |
| `--sourcemap` / `--sourcemap=inline` / `--no-sourcemap` | Bare means `external`: `<outFile>.map` next to the CSS plus a `sourceMappingURL` comment; `inline` embeds a data URI. Default off. Overrides `sourcemap` in the config. |
| `--strict-theme=<family,...>` / `--no-strict-theme` | Fail, before writing anything, when a named family is only partly declared by the project (see [Strict theme](#strict-theme-families-that-must-be-complete)). `--no-strict-theme` turns a config's `strictTheme` off for one run. |

An entry's extension decides how Dart Sass reads it. A `.uxdsl` entry carries
UXDSL's syntax through Sass; a `.css`, `.scss` or `.sass` entry
(`--entry src/app.css`, or `entry: './src/app.scss'` in the config) is read as
written, as plain Dart Sass reads it, so a dotted token there fails
(`UXD_SASS: expected "(".`). Name entries `.uxdsl`. How `@use` and `@import`
find files, which `@import`s stay CSS and what each extension decides are in
the `compile()` guide's [Sass inside `compile()`](compile.md#sass-inside-compile).

### `theme`

| Flag | Does |
| --- | --- |
| `--config <file>`, `-c` | The build config, when the theme file sits next to a config outside the current directory. |
| `--diff` | Only the families the theme file mentions, one row per leaf labeled `project` or `default`; a family mixing both is summarized on stderr. `$schema` is not a leaf. |
| `--contrast` | Check every text and border pair of the effective theme against WCAG, print the JSON report, exit 1 if any pair fails or a packaged exception is stale. Pairs a packaged exception covers (the canvas-identity families `surface`, `light`, `dark` used as a tone) are printed under `excepted`, never counted as passing; a clean exit says how many on stderr. Not combinable with `--diff` or `--strict-theme`. |
| `--strict-theme=<family,...>` | The same check as `build`'s, without building. |

`theme` takes no `--entry`/`--out`: it reads a theme, and works from a theme
file alone, with no build config. It prints the unknown-family warning `build`
prints, on stderr, so stdout stays one JSON document for `| jq` and scripts.

What it prints is the theme as written, not resolved colors: since stability
phase 5 the base palette references its own Colors collection, so a leaf your
theme does not override reads `"main": "color(purple.700)"` (and `--diff`
labels it `default`) rather than `#7e22ce`; the hex is under `colors.purple`
in the same document. A script that wants the final color resolves the
reference through the compiled CSS (`uxdsl build`) or `tokenValueToCss`
from `uxdsl/language`, not by reading the leaf as a color.

### `generate-entry`

| Flag | Does |
| --- | --- |
| `--src <dir>` | The directory scanned for `.uxdsl` files, subdirectories included. Default `./src`, or the working directory when it has no `src/`. |
| `--out <file>`, `-o` | The entry it writes. Default: `uxdsl-entry.uxdsl` in the `--src` directory. No file with the entry's file name is listed, in any directory under `--src`, as with an `--exclude` name: with `--out src/main.uxdsl`, `src/pages/main.uxdsl` is left out too, without a message. |
| `--first <a,b>` | The files to load first, in that order: paths relative to `--src`, comma-separated, `./` and `.uxdsl` optional. |
| `--exclude <a,b>` | File names to leave out, in any directory under `--src`. |

The entry has one `@use` per file, after a header that says how to rebuild it:

```text
/* AUTO-GENERATED FILE - DO NOT EDIT MANUALLY */
/* Generated by uxdsl generate-entry */
/* Run uxdsl generate-entry again, with the same options, after adding or removing a .uxdsl file. */

/* --- Application & Component Imports --- */
@use './variables' as variables;
@use './card' as card;
@use './components/card' as components-card;
```

- **The path** is the file's path relative to the entry's directory, starting
  with `./` (or `../`), without `.uxdsl` and without a partial's leading `_`
  (`_variables.uxdsl` is `./variables`). `%`, `#`, `?`, `'` and `\` are
  percent-encoded: `a#b.uxdsl` is `./a%23b`.
- **The namespace** is that path without its leading `./`, lowercased, with
  `-` for every character outside `a-z`, `0-9` and `-`, and `f-` in front of
  a leading digit or `-`: `2col.uxdsl` is `f-2col`, and from an entry in
  `src/app/`, `../components/card` is `f----components-card`. Two files that
  would share a namespace (`components/card.uxdsl` and `components-card.uxdsl`)
  get it in path order: the first keeps it, the next gets `-2`, then `-3`.
- **The order**, without `--first`: the files whose name contains `theme-def`,
  `layout`, `app` or `variables` first, then the others by path. With
  `--first`, the files it names, in its order, then every other file by path.
  An item that matches no file (with a suggestion), names a file the entry
  leaves out (an `--exclude` name, or a file with the entry's file name) or
  appears twice exits 1 and writes nothing, and so does a `--first` with no
  item.

Each file is its own Sass module. An entry that `@import`ed its files gave
them one scope; with `@use`, a file that reads another file's `$variable`,
mixin or `%placeholder` fails as `UXD_SASS` (`Undefined variable.`,
`Undefined mixin.`, `The target selector was not found.`), and three cases
compile differently, without an error: a call to another file's `@function`
stays in the CSS as written, a value an earlier file set for a variable that
another file declares `!default` no longer applies, and a project `@function`
named like a UXDSL function (`space()`) replaces the token only in a file
that `@use`s its file `as *` (or `@import`s it), and in a call through the
namespace (`helpers.space(2)`). Give each file its own `@use` for what it
reads:

```scss
// src/card.uxdsl reads $brand from src/_variables.uxdsl
@use './variables' as *;

.card { color: $brand; }
```

With `as *` the module's members keep their bare names. With a namespaced
`@use` (`@use './variables';`, `@use './helpers';`), write each one through
the namespace (`variables.$brand`, `helpers.double(4px)`): a bare variable or
mixin fails there, but a function called by its bare name stays in the CSS as
written, and one named like a UXDSL function stays the token, without an
error.

A module that a file configures with `@use … with (…)` must be configured
before anything else loads it: name the configuring file in `--first`, since a
file named like `variables` is otherwise listed first. When `generate-entry`
replaces an entry that listed its files with `@import`, it prints one
`[uxdsl] Warning:` that says so and points to the migration guide; it prints
nothing for a new entry or an entry already on `@use`.

A partial and a file of the same name side by side (`_card.uxdsl` beside
`card.uxdsl`), or a `.scss` file beside a `.uxdsl` file of the same name (in
the middle of a rename), make the path without its extension ambiguous: Dart
Sass's located `UXD_SASS: It's not clear which file to import` names both.
Rename one.

## Two files, two jobs

The **build config** says what to compile and where. It is a JavaScript
module, `uxdsl.config.cjs` or `uxdsl.config.js`:

```js
// @ts-check
/** @type {import('uxdsl/config').UxdslConfig} */
const config = {
  entry: './src/uxdsl-entry.uxdsl',
  outFile: './src/uxdsl.css',
  watch: ['src/**/*.uxdsl', 'src/**/*.css'],
  // sass: { silenceDeprecations: ['import'], quietDeps: true },
};

module.exports = config;
```

| Key | Does |
| --- | --- |
| `entry`, `outFile` | One entry and its output. |
| `builds` | Several entries: `[{ entry, outFile, includeTheme? }, …]`. Not combinable with a top-level `entry`/`outFile`. |
| `includeTheme` | Emit the `:root` definitions (default `true`). Per entry inside `builds`. |
| `watch` | Extra paths for `--watch`, beyond the entries, every file Dart Sass loaded for them, and the config/theme files. |
| `references` | `{ mode, externalTokens, css }` — the reference-integrity options (the package README, "Reference integrity"). This is its only home. |
| `strictTheme` | `['palette', 'breakpoints']`: the families that must be completely declared. |
| `sourcemap` | `false`, `'inline'` or `'external'`. Spelled like the flag. |
| `sass` | Dart Sass options for every entry: `{ silenceDeprecations?: string[], quietDeps?: boolean }`, the deprecation ids not to report (each is otherwise a `UXD_SASS_WARNING`) and whether to silence the deprecations of packages loaded from load paths or `pkg:`. |

`sass` is checked when the config loads, and the error names the file: a
value that is not an object, a key other than those two (`silenceDeprecation`
suggests `sass.silenceDeprecations`), a value of the wrong type, `sass` inside
a `builds` entry (it applies to every entry), and `silenceDeprecations` or
`quietDeps` written at the top level instead of inside `sass`. An id Dart Sass
does not know is its own warning, `UXD_SASS_WARNING: Invalid deprecation "…".`
`--entry`/`--out` reads no config, so no `sass` applies there, as no other key
does.

The config is type-checked by the editor through the `@type` line (`init`
writes it): `// @ts-check` makes the editor report in plain JavaScript, the
type sits on the `const` because on `module.exports = {…}` it checks nothing,
and it is a type import, not a `require`, so a project that cannot resolve
`uxdsl` from the config's directory (a global or `npx`-run CLI) loses the
type and not the build. `defineConfig` from `uxdsl/config` checks the
same way, at the cost of that `require`.

The **theme file** holds the theme — `breakpoints` included — and nothing
else. It sits next to the build config and is discovered by name, by this
CLI and by the PostCSS plugin, the Vite plugin and the Webpack loader alike:

```text
uxdsl.theme.cjs   uxdsl.theme.js   uxdsl.theme.json
```

It exports the theme object (or a function, sync or async, returning it):

```js
// uxdsl.theme.cjs
module.exports = {
  breakpoints: { xl: 1440 },
  fonts: { families: { ui: 'var(--font-geist-sans, Arial, sans-serif)' } },
};
```

```json
{
  "$schema": "./node_modules/uxdsl/schema/theme.schema.json",
  "palette": { "primary": { "main": "#7e22ce", "contrast": "#ffffff" } }
}
```

A family the file does not mention keeps the base theme's values
(`breakpoints`: `{ xs: 0, sm: 480, md: 768, lg: 1024, xl: 1280 }`); a family
it mentions partly keeps the base's other keys — `uxdsl theme --diff` shows
exactly which. `$schema` gives the editor completion and validation; the path
is relative to the file. Everything the file `require()`s locally is watched
too.

What each file refuses, with the new home in the message: a build config
carrying `theme`, `themeFile`, `breakpoints`, `output` (use `outFile`) or
`sourceMap` (spelled `sourcemap`); a theme file exporting the former
`{ theme, references }` wrapper; a `uxdsl.config.json`. A theme file whose
export looks like a build config (`entry`, `outFile`, `watch`, `builds`) gets
a warning naming the stray keys.

## Multiple entries, one shared theme

A theme entry defines the `:root` tokens once; component or CSS-Module entries
consume them with `includeTheme: false`:

```js
module.exports = {
  builds: [
    { entry: './src/theme.uxdsl', outFile: './src/theme.css' },
    { entry: './src/panel-a.uxdsl', outFile: './src/panel-a.module.css', includeTheme: false },
    { entry: './src/panel-b.uxdsl', outFile: './src/panel-b.module.css', includeTheme: false },
  ],
  watch: ['src/**/*.uxdsl'],
};
```

Every entry is compiled in memory before anything is written: a failure in any
one of them writes nothing. `--include-theme`/`--no-include-theme` overrides
every entry uniformly. An entry with `includeTheme: false` still validates
every reference against the theme; it just emits no `:root`.

A `.module.css` output must never define `:root` — CSS Modules loaders reject
it ("Selector :root is not pure") — so an entry named that way whose output
would still define `:root` fails before anything is written, naming the
entry; the fix is `includeTheme: false` on it. More than one entry emitting the
theme at all is a warning, not an error.

## Next.js: CSS Modules written in `.uxdsl`

Next.js compiles a `.module.scss` file with its own Sass, which reads UXDSL's
dotted tokens and `color()` tokens as Sass and stops at them
(`palette(primary.main)` is Dart Sass's `expected "("`, `color(white)` its
`$description: white is not a string.`), and writes a directive as
`@ds-surface (contained)`, which `uxdsl/postcss` refuses
(`UXD_SURFACE_ARGUMENT`). Write the module in `.uxdsl` instead, and let the
CLI compile it into a `.module.css` file that Next.js imports like any other
CSS Module:

```js
// uxdsl.config.cjs
module.exports = {
  builds: [
    { entry: './src/theme.uxdsl', outFile: './src/theme.css' },
    { entry: './src/components/panel.module.uxdsl', outFile: './src/components/panel.generated.module.css', includeTheme: false },
  ],
};
```

```scss
/* src/components/panel.module.uxdsl */
@use "sass:math";

$gap: math.div(48px, 3);

.panel {
  padding: $gap;
  border: 1px solid palette(primary.main);

  &__title {
    color: palette(primary.main);
    margin: 0 0 math.div($gap, 2);
  }
}
```

```jsx
// src/components/Panel.jsx
import styles from './panel.generated.module.css';

export function Panel({ title }) {
  return <section className={styles.panel}><h2 className={styles.panel__title}>{title}</h2></section>;
}
```

- Every module entry takes `includeTheme: false`: the theme comes from one
  global stylesheet (`src/theme.css` here, imported once from the root
  layout), and a `.module.css` file holding `:root` is not pure, so the CLI
  refuses to write one.
- Run `uxdsl build --watch` beside `next dev`, and `uxdsl build` before
  `next build` (`init` adds `uxdsl:watch` and `uxdsl:build` scripts).
- The generated files are build output: list them in `.gitignore`
  (`*.generated.module.css`).
- The CLI writes Dart Sass's CSS as it is: a module with non-ASCII text, a
  comment included, starts with `@charset "UTF-8";`, which Next.js accepts.

`fixtures/mig02-nextjs-cssmodules` in the repository builds such a module
with the installed CLI, runs `next build`, and reads its computed styles in
Chrome on the served page.

## Watch mode

`uxdsl build --watch` builds, then rebuilds when an entry, a file Dart Sass
loaded for it, the config and theme files (and whatever they `require()`
locally) or the `watch` globs change. The first build's dependency graph is
where the session starts, so the first change already rebuilds only the
entries that load the changed file. Every entry and every file Dart Sass
loaded is followed, whether or not a `watch` pattern matches it: a `.scss`
partial, a file outside the entry's directory or in `node_modules`, and an
entry the patterns miss, so a first build that failed recovers when the entry
is saved. A file is followed through its directory, which keeps an editor's
save by rename visible; the directory's other files are not followed. The
files followed are every entry and the files the last successful build of
each entry loaded. A file a build starts loading is followed once that build
succeeds, and the save that made the entry load it builds the entry once if
the file was last written more than 100 ms before that build started (2 s on
a file system that keeps whole seconds). A file written later, as a "save
all" or a branch switch that writes it with the entry can do, may build the
entry a second time and print its warnings twice.

It reloads the config and the theme from disk on every rebuild, never
re-triggers on its own output file, and survives errors. Every failed build of
the session, the first one included, prints `[uxdsl] build failed:` with the
location and frame a one-shot build prints (see [Diagnostics](#diagnostics));
a config that fails to load prints `[uxdsl] Error: … — watching for a fix...`.
Either way the last good CSS stays on disk until the next valid save. A source
change recompiles only the `builds` entries that depend on it; a config or
theme change rebuilds all. Deleting a file an entry still loads fails that
entry with `UXD_SASS` and keeps its CSS; creating the file again rebuilds it.
The same holds for a followed file's directory (`rm -rf shared/`, a switch to
a branch without it): it is watched for again from the nearest directory
above it that remains, so restoring it rebuilds the entries that load its
files, and every later edit rebuilds them too.

A partial a build could not find (`Can't find stylesheet to import.`) is
noticed when it appears only where a `watch` pattern matches it, since Dart
Sass does not report the paths it tried: with the default patterns, a new
`_x.uxdsl` under the entry's directory is; a new `.scss` partial, or one in
another directory, is picked up at the next save of a watched file. Add its
directory to `watch` (`'shared/**/*.scss'`) to have it noticed.

Output is written only when it changed, atomically (temp file plus rename), so
a reader never sees a truncated file and an unchanged entry keeps its mtime:

```text
[uxdsl] built src/uxdsl.css (50854 bytes)
[uxdsl] unchanged src/uxdsl.css (compiled output identical to the file on disk; not rewritten)
```

A `watch` entry is a glob when it has `*`, `?`, a `[…]` class, a `{…}` set or
an extglob (`@(…)`, `!(…)`, `+(…)`); the watcher follows its static base
directory (`src` for `src/**/*.uxdsl`, also when it is created after the
watcher started) and reports only the files the glob matches, dot-directories
included — the picomatch semantics chokidar 3 used. Anything else is a path:
a file, a directory (watched recursively) or one that does not exist yet. A
parenthesis alone is a path character, so `app/(marketing)/page.uxdsl` is the
file of that name. Directories no glob can reach (`src/a/b` for `src/*.uxdsl`)
are not traversed.

"Unchanged" is about the output, not the inputs. `UXDSL_DEBUG=1` logs which
config and theme files were discovered (and which external tokens were
loaded, never their values).

## Strict theme: families that must be complete

A theme is the base plus your override, merged key by key, so overriding
`palette.primary.main` alone keeps the base's `primary.dark` — and a green
button's hover comes out purple. `uxdsl theme --diff` shows the mix;
`--strict-theme` turns it into a build failure for the families you choose:

```bash
npx uxdsl build --strict-theme=palette,breakpoints
```

```js
// uxdsl.config.cjs
module.exports = { strictTheme: ['palette', 'breakpoints'] };
```

A scope is required. The former bare flag checked every family the project
touched, and the theme model *is* partial overrides — one `palette.primary.main`
over the base, one `typography_details` field — so it flagged the usage the
documentation recommends as "incomplete"; it had no correct use and is refused
with the scoped form spelled out. A family the project never declares is not
partial, so naming it never fails. `=true`/`=false` are refused too: to turn a
config's `strictTheme` off for a run, `--no-strict-theme`. A family name is
checked against the families the compiler knows (`Unknown theme family
"pallete" … Did you mean "palette"?`), and a stray comma is an error rather
than a silently shorter list.

`uxdsl theme --contrast` answers the question that follows — do the resulting
text and border pairs meet WCAG? It loads the exceptions shipped with the base
theme — three patterns for the canvas-identity families `surface`, `light`
and `dark` used as a tone, which follow the tone rather than a hex — and
reports each failing pair with its mode, component, tone, state and
breakpoint, and each excepted pair under `excepted` with the exception that
covers it. The base theme passes its own gate (since stability phase 5), so
with no override the command exits 0 and a failing pair is one your override
introduced; a pattern that your override leaves nothing to cover is reported
as stale.

## Source maps

```bash
npx uxdsl build --sourcemap            # external: writes <outFile>.map
npx uxdsl build --sourcemap=inline     # embeds the map as a data URI
```

Or `sourcemap: 'external'` in the config; the flag wins. A plain declaration
maps to its own line; a declaration the compiler rewrote (`density()`,
`palette()`, …) maps to the original one; the declarations a `@ds-button`
expands into map to the directive's line; a declaration from an imported
partial maps to that partial. The `:root` blocks generated from the theme are
left unmapped. Switching an output from `external` to `inline`/off retires its
own `.map`; a file at that path that is not a source map is never deleted.

## Diagnostics

Build failures name the source file, line, column and a frame of the author's
source, inside imported partials too; theme failures name the theme file and
the key path. Every diagnostic starts with its stable `UXD_*` code:

```console
$ npx uxdsl build
[uxdsl] Error: uxdsl.theme.cjs: UXD_EDGE_VALUE: Invalid token 1 (at radii.1).
```

A Dart Sass failure is `UXD_SASS`, followed by Dart Sass's own frame and
stack, every line indented by two spaces:

```console
$ npx uxdsl build
[uxdsl] Error: src/a.uxdsl:1:1: UXD_SASS: Can't find stylesheet to import.
    ╷
  1 │ @use './missing';
    │ ^^^^^^^^^^^^^^^^
    ╵
    src/a.uxdsl 1:1  root stylesheet
```

The frame shows the line as written, tokens such as `palette(primary.main)`
included. A UXDSL error prints PostCSS's frame of the author's line instead
(`> 18 |`, with a caret under the column). In a `builds` project the entry's
index and output come before the location:
`[uxdsl] Error: builds[1] (out/b.css): src/b.uxdsl:3:1: UXD_SASS: …`.

Every `compile()` warning goes to stderr as one line, and the exit status does
not change:

```console
[uxdsl] Warning: src/entry.uxdsl:1:9: UXD_SASS_WARNING: [import] Sass @import rules are deprecated and will be removed in Dart Sass 3.0.0.
[uxdsl] Warning: src/_helpers.uxdsl:1:11: UXD_FUNCTION_SHADOWED: @function space (src/_helpers.uxdsl:1) replaces UXDSL's space() in this build; rename it to use the token
[uxdsl] Warning: UXD_SASS_WARNING: 2 repetitive deprecation warnings omitted.
```

That is `<file>:<line>:<column>: <text>`, `<file>: <text>` when a warning has
a file and no line, or the text alone when it has no position, as Dart Sass's
own summary does: Dart Sass reports five warnings of each deprecation type,
then that summary. Each entry's warnings print as soon as the entry compiles,
before a later entry's error. A line with a file already printed in the same
build is not repeated (a partial two entries load). A line without a position
is the warning of the entry that reported it, so each entry prints its own,
even when two read the same: Dart Sass's summary counts what it omitted for
that entry, and an unknown id in `sass.silenceDeprecations` is reported by
every entry. Every build that recompiles an entry, in watch mode too, prints
that entry's warnings again. To stop
reporting a deprecation type, name it in the config's
`sass.silenceDeprecations` (`['import']`); `sass.quietDeps` silences the
deprecations of packages. A failed compile prints its error and not the
warnings Dart Sass reported before it.

`build` and `theme` warn about an unrecognized top-level theme family
(`color` instead of `colors`) — a typo that would otherwise compile into
nothing — once per session; the build still succeeds. Exit status is set
through `process.exitCode`, so `uxdsl theme --contrast | jq` gets the whole
document.

## Editor support

| What you get | In which file | How |
| --- | --- | --- |
| Types, completion and typo detection | `uxdsl.config.cjs` | the `// @ts-check` + `@type` header `init` writes |
| Completion and validation of families, fields and states | the theme JSON | one `$schema` line pointing at `uxdsl/schema/theme.schema.json` |
| Highlighting and completion | `.uxdsl` files | the `uxdsl-vscode` extension, installed from a `.vsix` built from the repository (`packages/uxdsl-vscode`, `npm run package`, then *Extensions: Install from VSIX*) |

The extension completes the built-in theme's roles, not your project's, and
has no live diagnostics. Only VS Code has been tested; the types and the schema
are ordinary TypeScript types and JSON Schema. In a monorepo whose
`node_modules` is hoisted, point `$schema` there
(`../../node_modules/uxdsl/schema/theme.schema.json`) or map it once
in `.vscode/settings.json` under `json.schemas`.

## Before you upgrade

`uxdsl theme` prints the effective theme, every family included. Save it
before and after, and diff:

```bash
npx uxdsl theme > effective.before.json
npm i -D uxdsl@<next>
npx uxdsl theme > effective.after.json
diff effective.before.json effective.after.json
```

This compares the theme, not the
compiled CSS: a change in how the compiler emits CSS from the same theme is
announced only in the
[CHANGELOG](https://github.com/rsantoyo-dev/uxdsl/blob/main/packages/uxdsl/CHANGELOG.md),
under `Visual changes`.
