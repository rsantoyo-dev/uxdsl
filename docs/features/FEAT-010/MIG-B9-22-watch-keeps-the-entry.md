## 1. Goal

Adding or removing a `.uxdsl` file never needs a manual command: when the
entry is one `generate-entry` wrote, `build --watch` regenerates it and
rebuilds. The playground, which kept a private copy of the generator, uses
the CLI's.

## 2. Sources

- Plan §5.2: "`uxdsl build --watch` regenerates the entry when a `.uxdsl` file
  is added or removed under the configured sources, so a new component shows
  up without `uxdsl generate-entry`."
- `bin/uxdsl.js`: `generateEntry` writes a three-line header
  (`/* AUTO-GENERATED FILE - DO NOT EDIT MANUALLY */`,
  `/* Generated by uxdsl generate-entry */`,
  `/* Run uxdsl generate-entry again, with the same options, after adding or removing a .uxdsl file. */`)
  and one `@use '<path>' as <namespace>;` per file (MIG-B9-14); `startWatch`
  classifies a changed file as full or selective; a file outside the known
  graph forces a full rebuild; `createWatcher` emits `add`, `unlink` and
  `change`.
- `packages/playground-nextjs/scripts/generate-uxdsl-entry.js`: the same
  algorithm with `PRIORITY_FILES = ['app/typography-roles.uxdsl', 'app/theme-def.uxdsl', 'app/layout.uxdsl', 'app/app.uxdsl']`
  and `EXCLUDED_FILES = ['uxdsl-entry.uxdsl']`, writing 41 `@import` lines;
  `package.json` runs it in `uxdsl:build` and `uxdsl:watch`.
- `src/app/app.uxdsl` imports `../components/RussianDoll.uxdsl`, which the
  entry also lists: with `@import` semantics under Sass that file is emitted
  twice; with `@use` once.

## 5. Contract

- **E1 — A generated entry records how it was generated.** `generate-entry`
  writes, in its header, one comment line with its own invocation
  (`/* uxdsl generate-entry --src ./src --out ./src/app/uxdsl-entry.uxdsl --first a,b --exclude c */`,
  paths relative to the config's directory). `uxdsl generate-entry` run with
  no arguments in a project whose configured entry carries that line re-runs
  that exact invocation (idempotent: running it twice changes nothing).
- **E2 — Watch regenerates it.** When the configured entry (single or any
  `builds[]` entry) is a generated one, `build --watch` reacts to `add`,
  `unlink` and rename events of `.uxdsl` files under that entry's `--src`
  by regenerating the entry with the recorded invocation, then rebuilding
  through the normal path. The regeneration is logged as
  `[uxdsl] regenerated <entry> (<n> files)`. A `change` event never
  regenerates.
- **E3 — A hand-written entry is never rewritten.** An entry without the
  generated header is left alone; adding a file next to it prints nothing
  special (today's behavior).
- **E4 — The playground uses the CLI.** `scripts/generate-uxdsl-entry.js` is
  deleted; `package.json`'s `uxdsl:build` and `uxdsl:watch` call
  `uxdsl generate-entry --src src --out src/app/uxdsl-entry.uxdsl --first app/typography-roles.uxdsl,app/theme-def.uxdsl,app/layout.uxdsl,app/app.uxdsl`
  (the same four files first, in the same order), then `uxdsl build`. With
  MIG-B9-20 merged, the generated theme file carries the marker and the
  playground's `uxdsl.theme.cjs` is unchanged.
- **E5 — No double emission.** `src/app/app.uxdsl` no longer imports
  `RussianDoll.uxdsl` (the entry lists it); the compiled `uxdsl.css` contains
  each rule once. The before/after diff of `src/app/uxdsl.css` is explained
  rule by rule (order within the priority files preserved; the duplicate
  removed).
- **E6 — The site is unchanged in Chrome.** The browser walk passes; the
  visual comparison harness (`fixtures/playground-browser/compare.js`)
  reports no unintended difference.

Must stay byte-identical: everything but the playground's entry and the
duplicate rule.

## 6. Out of scope

- A glob `@use` form: not a Sass feature; the generated entry is the
  mechanism.
- Watching for new files when no generated entry exists.

## 7. Approach and traps

- Chokidar 4 emits `add`/`unlink` for files under watched roots; the watch
  roots already include each entry's directory and the configured globs
  (`normalizeWatchGlobs`); `--src` outside those roots must be added to the
  roots when the entry is generated.
- Regeneration must happen before `classify`: a brand-new file is not in any
  dependency set, so today it triggers a full rebuild that compiles the old
  entry; regenerate first, then let the full rebuild run.
- The recorded invocation line is parsed with the same `parseCommandArgv` the
  CLI uses, never with an ad hoc regex.
- Stop rule: if the playground's compiled CSS differs beyond the duplicate
  removal and ordering, stop and record (it would mean `--first` or the
  default ordering disagrees with the old script).

- **Contract as delivered, where it differs from §5** (the amended reading the scout recorded, which the code follows):
  - **E1.** `generate-entry` writes `/* uxdsl generate-entry --src <src> --out <out>[ --first <a,b>][ --exclude <c,d>] */` as the header's third line, after `/* Generated by uxdsl generate-entry */`. `--src` and `--out` are always written, POSIX and relative to the working directory, as `./x` (`.` for the directory itself); `--first` items relative to `--src`, without `./`, with `.uxdsl`. A value with whitespace, `"`, `\`, `*/` or `#{` is a JSON string (`*/` as `*\/`, `#{` as `\u0023{`, since Dart Sass interpolates in a comment), and one starting with `-` follows an `=`. The line is read back by splitting it into words and passing them to `parseCommandArgv`, with no regex per flag; a positional word, `--help` or `--version` is refused. The fourth line now says that `build --watch` and `generate-entry` with no arguments regenerate the entry from that line. With no option and no argument, `generate-entry` loads the config as `build` does and re-runs, in config order, every configured entry's recorded line, each planned before any is written; an unparsable line, an `--out` that is not the entry, or a `--first` file that is gone exits 1, naming the entry, and writes nothing. When no configured entry records one, the file the defaults write is re-run from its own recorded line when it has one (owner flag 5), and the defaults apply when it has none. Every write goes through `commitFileIfChanged`, so a second run keeps bytes, mtime and inode.

A `change` never regenerates, nor does an event on a configured entry. A regeneration that fails prints `[uxdsl] Error: regenerating <entry>: …`, writes nothing, and the build runs as it would without it.
