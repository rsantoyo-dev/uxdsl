# UXDSL 0.5.0-beta.4

Published from main commit `be52cf609e1fd11aea7fde986a480be71a5c5f92`, under npm `latest` at the owner's explicit request. Both `latest` and `beta` point to this prerelease, matching how `0.5.0-beta.1`, `0.5.0-beta.2` and `0.5.0-beta.3` were published. It remains beta software; a dist-tag does not change its maturity.

All five distribution packages use version `0.5.0-beta.4`: `postcss-uxdsl`, `uxdsl-core`, `vite-plugin-uxdsl`, `uxdsl-webpack-loader`, and `uxdsl-cli`.

This release closes [FEAT-005](../features/FEAT-005-beta4-zero-friction-cli.md), based on a second round of real-consumer verification against beta.3. It is entirely additive and opt-in — no existing `uxdsl.config.cjs`/`uxdsl.theme.config.*` changes behavior, and no migration steps are required:

- `uxdsl build`/`watch` now watch every local module a build config or theme file `require()`s transitively, not just the top-level file — editing a module a config/theme delegates to (`module.exports = require('./real-config.js')`, or a theme reading `require('./theme-data.json')`) now triggers a rebuild on its own. The CLI's own README previously documented this gap as expected behavior.
- `uxdsl build`/`watch` accept `--strict-theme` (or `strictTheme: true` in `uxdsl.config.cjs`), reusing the same check `uxdsl theme --strict` already ran — fails before writing anything if a declared theme family ended up partially filled from `DEFAULT_THEME`. Defaults to `false`.
- `uxdsl init --multi` scaffolds a theme entry plus one example component entry (a `builds` array) directly, instead of hand-writing it from the README.

Read [the migration guide](../../packages/postcss-uxdsl/docs/migration.md) (a short additive-changes note — no migration steps needed) and [changelog](../../packages/postcss-uxdsl/CHANGELOG.md) before upgrading from 0.5.0-beta.3.

Preparation checks: the full engine/core/CLI test suites (72 CLI tests including real chokidar/subprocess watch-mode coverage and two revert-and-confirm-failure cycles during development), the `mig-b2-03-cli-init` fixture extended with `init --multi` coverage, and the `mig-b4-04-release` fixture (5 real tarballs: `init --multi` end to end, a build-config-level nested `require()` combined with `--strict-theme` failing on a partial theme and passing on a complete one, and a real `uxdsl watch` subprocess rebuilding from an edit to only the nested file) all passed. `mig-b2-05-release` and `mig-b3-06-release` were re-verified passing unchanged. A pre-existing, unrelated drift was also caught and fixed while building this release's gate: `theme-manifest.json`'s `uxdslVersion` had gone stale at `0.5.0-beta.2` after the beta.3 publish bumped every package's version without a `generate:language` re-run; the root `npm test` (227 tests) now passes clean. These checks do not establish complete browser or accessibility coverage.

Published via `node scripts/release.js --version 0.5.0-beta.4 --tag beta` (dependency order: `postcss-uxdsl` → `uxdsl-core` → `vite-plugin-uxdsl` → `uxdsl-webpack-loader` → `uxdsl-cli`), then `npm dist-tag add <pkg>@0.5.0-beta.4 latest` for each package. Like beta.3, this publish succeeded with no OTP/2FA prompt.

Registry verification confirmed both `latest` and `beta` tags at `0.5.0-beta.4` for every package (allowing for npm's normal post-publish indexing delay on four of the five packages for the initial publish; the `latest` tag addition propagated immediately for all five). A fresh install of `postcss-uxdsl@beta` and `uxdsl-cli@beta` from the real registry into an isolated directory confirmed all three new features end to end: `uxdsl init --multi` scaffolding a working `builds` project, `uxdsl build --strict-theme` passing on a zero-config project and failing (naming the family, exit code 1) on a partial theme declared via `uxdsl.theme.config.cjs`, and `uxdsl theme --diff` (from beta.3) still working correctly — confirming the published tarballs work end to end outside the monorepo.
