## 4. Philosophy — state it, and make the system enforce it

1. **Write the five principles** in one place and use them everywhere (root
   README intro, `/docs/introduction`, the top of `AGENTS.md`):
   1. Components name decisions, never values.
   2. The theme resolves each decision for its context (viewport and mode
      today).
   3. A decision that cannot be honoured is an error: nothing fails
      silently, and an illegible combination is not representable.
   4. The theme is data — the same for build, runtime, audit and agents.
   5. It is CSS: every extension exists only because intent needed a word.
   Headline: *a design-system language that neither people nor agents can
   break without noticing.*
2. **One vocabulary for "context"** (documentation only): breakpoints and
   `modes.dark` are both contexts the theme maps a decision onto. Say so in
   the docs; it is the frame container and preference contexts would later
   fit into (§5.6).
3. **Make illegible combinations unrepresentable — the one breaking item.**
   The canvas-identity families `surface`, `light`, `dark` used as a tone on
   `outlined`, `flat` or `underline`, or as a contained Input's focus border,
   draw the canvas color on the canvas. Today they compile and the contrast
   gate excepts them (111 pairs through three pattern records). Make them a
   compile error with its own `UXD_*` code and a hint ("use them as a tone on
   `contained` only"), catalogued in `DIAGNOSTIC_CATALOG`; drop the three
   pattern exceptions; the gate should then report 0 failing and 0 excepted
   for the base theme. Check the playground and the doc examples for uses
   first. Must land before 1.0.
4. **Recorded non-change:** ordinal token keys (`density(4)`) stay. Intent
   lives in roles; renaming scales is not on the table.

## 5. User-experience improvements (none changes how styles are written)

Ordered by the value they give a daily user. 1–3 are small and should be in
beta.9; 4 and 5 are medium; 6 is a design note only.

1. **`uxdsl doctor [--fix]`.** Inspects a project and lists, file by file,
   what to change for the installed version: removed commands in
   `package.json` scripts (`uxdsl watch`), old theme file names, removed
   config keys, old package names and import paths, removed or dashed
   grammar in `.uxdsl` files, the agent-guide path. `--fix` applies the
   mechanical ones by reusing the shipped codemods. Every message points at
   the `DIAGNOSTIC_CATALOG` entry. Test it on a copy of a beta.6 project and
   on `story-radar`.
2. **No manual entry step.** `uxdsl build --watch` regenerates the entry when
   a `.uxdsl` file is added or removed under the configured sources, so a new
   component shows up without `uxdsl generate-entry`. (Alternative if that is
   not enough: a glob `@import "./components/**/*.uxdsl"` in the entry only.)
   Components are unaffected either way.
3. **One-page language reference**, generated from the code: every value
   function with its grammar and one example with its output, every
   directive with its arguments, every theme family with its shape and key
   ranges, every `UXD_*` code with its fix. In the site (`/docs/language`,
   `/docs/theme`, `/docs/diagnostics` already exist from phase 6 — make them
   complete and generated) and linked from the README.
4. **See a token's value where it is written.** Editor hover on
   `density(4)` → `0.75rem · md 1rem · xl 1.5rem`, resolved with the
   **project's** theme, not the base theme (this is MIG-B7-13, previously
   blocked on D-11: treat it as decided for beta.9). Same data as a small
   `uxdsl explain density(4)` CLI command, which the hover can call.
5. **Emit only what is used — opt-in.** A build option (for example
   `emit: 'used'`) that emits only the tokens and roles the compiled sources
   reference (the compiler already resolves every reference). It is **not**
   the default and must say so: `applyTheme` can only change custom
   properties that exist on the page, so a pruned build cannot apply an
   unused token at run time. Measure the one-card, one-button app before and
   after (today 38–48 KB).
6. **Container context — design note only.** Write down how a theme would
   say "this density responds to the component's container" while components
   keep writing `density(4)` (the container would be declared by a role or a
   single declaration, not by every component), and how it relates to §4.2.
   Implementation is after 1.0 unless the owner decides otherwise.

## 6. Presentation and adoption

UXDSL is the owner's front-end calling card and their working experience
written down as a point of view — and the goal is that other people use it.
For a CSS tool from one author, people adopt in this order: they understand
it in a minute, try it in five, fit it into a project they already have, and
trust it will not be abandoned. Beta.9 works on all four; none of this adds
authoring syntax.

1. **Say who it is for.** One primary audience in the README, the home page
   and the introduction: teams maintaining a design system or an app with
   several themes or brands (white-label, multi-client) — the theme JSON,
   `applyTheme` and the contrast gate are exactly their problem. Secondary,
   named once each: teams that build with AI coding agents ("a design system
   an agent cannot break without noticing"), and people who want disciplined
   tokens without utilities in their markup.
2. **The first impression is the owner's.** The root README and the site's
   home page are what a visitor reads in the first two minutes: they show the
   thesis, the five-line example with its real output, who it is for and how
   to try it — no release history (§3.3 rewrites them; this sets their
   order). Badges for CI and the npm version.
3. **"Why UXDSL", in the owner's voice.** A short first-person page (and the
   first article): the problem seen in real projects (values copied because
   they matched, breakpoints repeated per component, palettes that said a
   color instead of a role), the idea, and what it does not try to be. It is
   written **with the owner** from their own account; an agent drafts only
   from what the owner tells it, never invents the experience.
4. **Try it in five minutes, without installing.** Two examples that open in
   the browser (StackBlitz or CodeSandbox), Next.js and Vite, where changing
   `densities.4` or a palette color in the theme visibly changes the page.
   Linked from the README and the quick start. (`npm create uxdsl` can come
   later.)
5. **Fit it into an existing project — the primary quick start.** The path
   already exists since phase 4: add `'uxdsl/postcss': { includeTheme: false }`
   to `postcss.config.js`, write `@uxdsl theme;` once in the global
   stylesheet, use `density()`/`palette()` in one component. Make it the
   first quick start ("one line of config, one token in one file"), with the
   CLI path second. State the low lock-in plainly: the output is ordinary CSS
   custom properties, so leaving UXDSL is cheap.
6. **Signals that it is maintained.** `CONTRIBUTING.md` (part of §3.3),
   issue templates (bug, question, idea), a short public roadmap (beta.9 →
   1.0 → after 1.0), and the stability policy written as `STABILITY.md`
   (audit §5.5) so "can I use this in production" has an answer. The VS Code
   extension on the Marketplace (§3.2) is also a discovery channel.
7. **Curate what a visitor sees.** The planning and evidence trail
   (`docs/features/**`, mostly in Spanish, story IDs, evidence tables) stays
   as the project's internal record, but a visitor must not have to wade
   through it: the README links product docs only, and `docs/` gets a short
   index that says which folders are product documentation and which are
   internal history.
8. **Not in beta.9, on purpose:** new features meant to attract users
   (container queries, a Tailwind bridge, Figma/DTCG import). Good ideas for
   after 1.0, when users ask for them; before that they add surface and
   delay stability, which is what drives adoption.

**Later (after beta.9, not a beta.9 goal):** a measurable adoption target —
for example five external projects using UXDSL and reporting back before
1.0. `story-radar` is the first.

### 7.2 One component per concept

A small design-system layer for the playground, every piece styled only with
UXDSL roles and tokens, used by the home page and every documentation page
alike — no page-specific copy of a card, a demo frame or an editor:

- **`Button`** — `@ds-button(role [tone] [size])`; every clickable control.
- **`Field`** (input, textarea, select) — `@ds-input(role …)`; every form control.
- **`Card` / `Panel`** — `@ds-surface(role …)`; every container.
- **`CodeBlock`** — the only way code is shown (one highlighter, one frame,
  scroll inside, light/dark), including the "you write / you get" pair.
- **`DemoFrame`** — the only interactive demo container: a live preview, the
  UXDSL that produced it, its compiled CSS, and optionally a resize handle
  and a theme editor. The home page's resize frame and every token page's
  demo are the same component with different content.
- **`TokenEditor`** — one editor for any theme value (today the Density,
  Space and Typography edit dialogs and the JSON editor are separate
  implementations), applying through `applyTheme`.
- **`Section`, `PageTitle`, `Text`** — page structure and text through
  `@ds-typo` roles only.

Each component owns one `.uxdsl` compiled as a CSS Module (the owner's
pattern); only page layout and the theme are global. Components are deleted
as they are absorbed; the target is roughly a third of today's 55.

### 7.3 Every principle demonstrated, live

One demo per principle, built from the components above, each driving the
real API rather than describing it:

1. **Components name decisions, never values** — a component next to its
   compiled CSS; edit the theme value and the component changes while its
   source does not (`DemoFrame` + `TokenEditor`).
2. **The theme resolves each decision for its context** — the resize frame
   (viewport) and the light/dark switch (mode) on the same component, with a
   readout of the live custom-property values.
3. **A decision that cannot be honoured is an error** — an editor where
   typing an undefined token, a wrong breakpoint or an illegible tone
   (§4.3) shows the real `UXD_*` diagnostic and its fix, from the real
   compiler running in the page.
4. **The theme is data** — one JSON edited once, seen in three places at
   the same time: the page (`applyTheme`), the contrast report
   (`checkThemeContrast`) and the CLI's `uxdsl theme --diff` view.
5. **It is CSS** — the compiled output is plain CSS custom properties; a
   native-CSS escape hatch shown on the same component.

### 7.4 Nothing manual, nothing hardcoded — enforced by a test

Extend the capability ratchet (`scripts/lib/capabilities.js`) into a strict
check that **fails** on, in playground sources: a literal `font-size`; a
hand-written `var(--uxdsl__…)`; `px` on spacing, edge or shadow
properties; a hex, `rgb()` or `hsl()` color outside theme JSON; a
hand-written `@media`; a `style={{ }}` carrying a literal (allowed: a
theme-derived value passed as a custom property, e.g. a measured width for the
resize frame); a `<button>`, `<input>`, `<textarea>` or `<pre>` outside its
one component. A short allowlist file records each remaining exception with
a one-line reason and the test counts it. Expected exceptions: literal code
*samples* shown as text (strings, not styles), and SideNav's
`@media (min-width: 1024px)`, which exists because a directive cannot be
applied from a named breakpoint — keep it as the single documented exception
(adding syntax for it is out of beta.9's scope), and say so on the page that
documents directives. `not-found`'s `@media (min-width: 600px)` becomes a
breakpoint function.

The phase-B visual comparison harness (`fixtures/playground-browser`) runs
before and after each unification step; intended visual changes are
declared, everything else must be identical. The capability matrix stays at
0 gaps and the browser walk green (no overflow, focus visible, contrast page
equal to Node).
