# UXDSL 0.5.0-beta.9 — plan (2026-10-08)

Written for whoever implements beta.9 (an agent or the owner). Read
`docs/audits/2026-09-29-auditoria-estabilidad.md` (the audit and the 1.0
contract) and `docs/audits/2026-10-07-handoff-stability.md` (working rules,
§2) first. Nothing in this file is done yet unless it says so.

## Vision (owner, 2026-10-09)

> "Quiero que sea la mejor librería en la historia — si no la más popular,
> la más interesante para resolver todos los gaps."

- **The most interesting CSS library, not necessarily the most popular:** one
  that closes the gaps the others leave.
- **It works like normal SCSS**, so a team writes what it already knows.
- **The author never writes a media query:** responsiveness belongs to the
  design system.
- **A design-system engine, inspired by Material UI's — but from CSS:**
  palette, spacing, breakpoints, typography variants, component variants with
  states, written as a CSS language and compiled, with no JavaScript runtime
  required.
- **Everything is input; the decisions are ours** (the owner's, with Claude).
  Proposals — from Press Craftor, from the audit, from Claude — are recorded
  so the best path is chosen with everything in view. Recording something
  does not commit to doing it.

**Origin (owner, 2026-10-09):** UXDSL is inspired by Material UI's theme
engine. That was the initial idea: bring its model to CSS. Inspired by, not
a copy or a port. It shares the model: a palette with main, light, dark and
contrast variants, a spacing scale, the `xs sm md lg xl` breakpoints,
responsive values per breakpoint, typography variants, and component
variants with states. It goes its own way where CSS and its principles lead:
it needs neither React nor a JavaScript runtime, responsiveness lives in the
theme (Density), the theme is data shared by build, runtime, audit and
agents, and a decision that cannot be honoured is an error, not a silent
fallback.

### The adoption ladder

The vision is a ladder; each step gives a reason to take the next one:

1. **Entering costs nothing:** rename `.scss` to `.uxdsl` and everything
   keeps working (§9). For an MUI team, most of the theme it already has can
   come along too (D-11).
2. **Value arrives gradually:** tokens and roles replace loose values, one
   file at a time, with `uxdsl migrate --suggest` showing where to start
   (§8.2).
3. **Guarantees come with it:** components never write a breakpoint, nothing
   fails silently, contrast is checked — UXDSL's "strict mode", which
   `uxdsl audit --check` can embody (§8.2).

**Precedent.** This is the adoption pattern that worked twice in front-end
tooling. Sass stayed niche with its indented syntax and took off with SCSS in
Sass 3, when every CSS file became valid SCSS. TypeScript won the same way:
every `.js` file is valid `.ts`, and types are added where they pay.
**UXDSL is to SCSS what TypeScript is to JavaScript.**

### Guardrails (the risks of this vision, turned into rules)

1. **Scope.** The vision is broad and the maintainer is one person; the real
   risk is never reaching a stable version. The ladder is the filter: work
   that does not serve one of its three steps waits until after 1.0, however
   interesting.
2. **"Rename and it works" must be 100% true.** One `.scss` that breaks
   after the rename costs more trust than ten features earn. Hence the large
   real SCSS codebase in §9.5 is the guarantee of the promise, not a detail.
3. **The Sass dependency is outside our control** (its evolution, such as
   `@import`'s removal in Dart Sass 3). Test against the supported Sass
   versions and track its deprecations.
4. **"Never write a media query" must be literally true**, or it becomes a
   trap: close D-2, and keep the "context" model (§4.2) ready to absorb
   containers (D-3), the modern expectation for components.

### The engine, measured against Material UI

| Material UI | UXDSL | Gap or difference |
| --- | --- | --- |
| `theme.palette.primary.main/light/dark/contrastText` | `palette(primary.main/light/dark/contrast)` | Same model |
| `theme.spacing(n)` | `space(n)`; `density(n)` is spacing with its responsive steps in the theme | UXDSL adds theme-level responsiveness |
| Breakpoints `xs sm md lg xl` | `xs()` … `xl()`, same names | Same |
| `sx={{ p: { xs: 1, md: 2 } }}` | `padding: xs(space(1)) md(space(2))` | Same idea, written in CSS |
| Typography variants (`h1` … `caption`) | `@ds-typo(role)` | MUI's Typography has no margin unless asked (`gutterBottom`); UXDSL roles emit margins (D-6) |
| `components.MuiButton` variants, style overrides, states | `buttons` roles with states; `@ds-button(role tone size)` | Custom-role inheritance differs (D-5) |
| `theme.shadows[n]`, `shape.borderRadius` | `shadow(n)`, `radius(n)` | Same |
| Color schemes (light/dark as CSS variables) | `modes.dark` + `data-theme` | MUI allows several schemes; UXDSL only `dark` |
| Nested `ThemeProvider` | — | **Gap**: scoped palettes do not reach composite tokens (D-4, Press Craftor F‑16) |
| `createTheme` in JS, styles at run time (Emotion) | A JSON theme compiled to CSS; `applyTheme` optional at run time | UXDSL needs no JavaScript to render |

## 4. Philosophy — state it, and make the system enforce it

1. **Write the five principles** in one place and use them everywhere (root
   README intro, `/docs/introduction`, the top of `AGENTS.md`):
   1. Components name decisions, never values.
   2. The theme resolves each decision for its context (viewport and mode
      today).
   3. A decision that cannot be honoured is an error: nothing fails
      silently, and an illegible combination is not representable.
   4. The theme is data — the same for build, runtime, audit and agents.
   5. It is CSS: every extension exists only because intent needed a word.
   Headline: *a design-system language that neither people nor agents can
   break without noticing.*
2. **One vocabulary for "context"** (documentation only): breakpoints and
   `modes.dark` are both contexts the theme maps a decision onto. Say so in
   the docs; it is the frame container and preference contexts would later
   fit into (§5.6).
3. **Make illegible combinations unrepresentable — the one breaking item.**
   The canvas-identity families `surface`, `light`, `dark` used as a tone on
   `outlined`, `flat` or `underline`, or as a contained Input's focus border,
   draw the canvas color on the canvas. Today they compile and the contrast
   gate excepts them (111 pairs through three pattern records). Make them a
   compile error with its own `UXD_*` code and a hint ("use them as a tone on
   `contained` only"), catalogued in `DIAGNOSTIC_CATALOG`; drop the three
   pattern exceptions; the gate should then report 0 failing and 0 excepted
   for the base theme. Check the playground and the doc examples for uses
   first. Must land before 1.0.
4. **Recorded non-change:** ordinal token keys (`density(4)`) stay. Intent
   lives in roles; renaming scales is not on the table.

## 5. User-experience improvements (none changes how styles are written)

Ordered by the value they give a daily user. 1–3 are small and should be in
beta.9; 4 and 5 are medium; 6 is a design note only.

1. **`uxdsl doctor [--fix]`.** Inspects a project and lists, file by file,
   what to change for the installed version: removed commands in
   `package.json` scripts (`uxdsl watch`), old theme file names, removed
   config keys, old package names and import paths, removed or dashed
   grammar in `.uxdsl` files, the agent-guide path. `--fix` applies the
   mechanical ones by reusing the shipped codemods. Every message points at
   the `DIAGNOSTIC_CATALOG` entry. Test it on a copy of a beta.6 project and
   on `story-radar`.
2. **No manual entry step.** `uxdsl build --watch` regenerates the entry when
   a `.uxdsl` file is added or removed under the configured sources, so a new
   component shows up without `uxdsl generate-entry`. (Alternative if that is
   not enough: a glob `@import "./components/**/*.uxdsl"` in the entry only.)
   Components are unaffected either way.
3. **One-page language reference**, generated from the code: every value
   function with its grammar and one example with its output, every
   directive with its arguments, every theme family with its shape and key
   ranges, every `UXD_*` code with its fix. In the site (`/docs/language`,
   `/docs/theme`, `/docs/diagnostics` already exist from phase 6 — make them
   complete and generated) and linked from the README.
4. **See a token's value where it is written.** Editor hover on
   `density(4)` → `0.75rem · md 1rem · xl 1.5rem`, resolved with the
   **project's** theme, not the base theme (this is MIG-B7-13, previously
   blocked on D-11: treat it as decided for beta.9). Same data as a small
   `uxdsl explain density(4)` CLI command, which the hover can call.
5. **Emit only what is used — opt-in.** A build option (for example
   `emit: 'used'`) that emits only the tokens and roles the compiled sources
   reference (the compiler already resolves every reference). It is **not**
   the default and must say so: `applyTheme` can only change custom
   properties that exist on the page, so a pruned build cannot apply an
   unused token at run time. Measure the one-card, one-button app before and
   after (today 38–48 KB).
6. **Container context — design note only.** Write down how a theme would
   say "this density responds to the component's container" while components
   keep writing `density(4)` (the container would be declared by a role or a
   single declaration, not by every component), and how it relates to §4.2.
   Implementation is after 1.0 unless the owner decides otherwise.

## 6. Presentation and adoption

UXDSL is the owner's front-end calling card and their working experience
written down as a point of view — and the goal is that other people use it.
For a CSS tool from one author, people adopt in this order: they understand
it in a minute, try it in five, fit it into a project they already have, and
trust it will not be abandoned. Beta.9 works on all four; none of this adds
authoring syntax.

1. **Say who it is for.** One primary audience in the README, the home page
   and the introduction: teams maintaining a design system or an app with
   several themes or brands (white-label, multi-client) — the theme JSON,
   `applyTheme` and the contrast gate are exactly their problem. Secondary,
   named once each: teams that build with AI coding agents ("a design system
   an agent cannot break without noticing"), and people who want disciplined
   tokens without utilities in their markup.
2. **The first impression is the owner's.** The root README and the site's
   home page are what a visitor reads in the first two minutes: they show the
   thesis, the five-line example with its real output, who it is for and how
   to try it — no release history (§3.3 rewrites them; this sets their
   order). Badges for CI and the npm version.
3. **"Why UXDSL", in the owner's voice.** A short first-person page (and the
   first article): the problem seen in real projects (values copied because
   they matched, breakpoints repeated per component, palettes that said a
   color instead of a role), the idea, and what it does not try to be. It is
   written **with the owner** from their own account; an agent drafts only
   from what the owner tells it, never invents the experience.
4. **Try it in five minutes, without installing.** Two examples that open in
   the browser (StackBlitz or CodeSandbox), Next.js and Vite, where changing
   `densities.4` or a palette color in the theme visibly changes the page.
   Linked from the README and the quick start. (`npm create uxdsl` can come
   later.)
5. **Fit it into an existing project — the primary quick start.** The path
   already exists since phase 4: add `'uxdsl/postcss': { includeTheme: false }`
   to `postcss.config.js`, write `@uxdsl theme;` once in the global
   stylesheet, use `density()`/`palette()` in one component. Make it the
   first quick start ("one line of config, one token in one file"), with the
   CLI path second. For an SCSS project the first step is simpler still:
   rename `.scss` to `.uxdsl` and keep building (§9). State the low lock-in plainly: the output is ordinary CSS
   custom properties, so leaving UXDSL is cheap.
6. **Signals that it is maintained.** `CONTRIBUTING.md` (part of §3.3),
   issue templates (bug, question, idea), a short public roadmap (beta.9 →
   1.0 → after 1.0), and the stability policy written as `STABILITY.md`
   (audit §5.5) so "can I use this in production" has an answer. The VS Code
   extension on the Marketplace (§3.2) is also a discovery channel.
7. **Curate what a visitor sees.** The planning and evidence trail
   (`docs/features/**`, mostly in Spanish, story IDs, evidence tables) stays
   as the project's internal record, but a visitor must not have to wade
   through it: the README links product docs only, and `docs/` gets a short
   index that says which folders are product documentation and which are
   internal history.
8. **Not in beta.9, on purpose:** new features meant to attract users

**Later (after beta.9, not a beta.9 goal):** a measurable adoption target —

## 7. The playground: one component per concept, every principle demonstrated, nothing hardcoded

**Owner requirement (2026-10-08).** The playground is UXDSL's reference
implementer and its demo: the components on the home page and in the
documentation demos must be **unified into one component per concept**, the
site must **demonstrate each of the five principles** (§4.1), and it must
**use UXDSL in its entirety — nothing written by hand, nothing hardcoded.**

### 7.2 One component per concept

A small design-system layer for the playground, every piece styled only with
UXDSL roles and tokens, used by the home page and every documentation page
alike — no page-specific copy of a card, a demo frame or an editor:

- **`Button`** — `@ds-button(role [tone] [size])`; every clickable control.
- **`Field`** (input, textarea, select) — `@ds-input(role …)`; every form control.
- **`Card` / `Panel`** — `@ds-surface(role …)`; every container.
- **`CodeBlock`** — the only way code is shown (one highlighter, one frame,
  scroll inside, light/dark), including the "you write / you get" pair.
- **`DemoFrame`** — the only interactive demo container: a live preview, the
  UXDSL that produced it, its compiled CSS, and optionally a resize handle
  and a theme editor. The home page's resize frame and every token page's
  demo are the same component with different content.
- **`TokenEditor`** — one editor for any theme value (today the Density,
  Space and Typography edit dialogs and the JSON editor are separate
  implementations), applying through `applyTheme`.
- **`Section`, `PageTitle`, `Text`** — page structure and text through
  `@ds-typo` roles only.

Each component owns one `.uxdsl` compiled as a CSS Module (the owner's
pattern); only page layout and the theme are global. Components are deleted
as they are absorbed; the target is roughly a third of today's 55.

### 7.3 Every principle demonstrated, live

One demo per principle, built from the components above, each driving the
real API rather than describing it:

1. **Components name decisions, never values** — a component next to its
   compiled CSS; edit the theme value and the component changes while its
   source does not (`DemoFrame` + `TokenEditor`).
2. **The theme resolves each decision for its context** — the resize frame
   (viewport) and the light/dark switch (mode) on the same component, with a
   readout of the live custom-property values.
3. **A decision that cannot be honoured is an error** — an editor where
   typing an undefined token, a wrong breakpoint or an illegible tone
   (§4.3) shows the real `UXD_*` diagnostic and its fix, from the real
   compiler running in the page.
4. **The theme is data** — one JSON edited once, seen in three places at
   the same time: the page (`applyTheme`), the contrast report
   (`checkThemeContrast`) and the CLI's `uxdsl theme --diff` view.
5. **It is CSS** — the compiled output is plain CSS custom properties; a
   native-CSS escape hatch shown on the same component.

### 7.4 Nothing manual, nothing hardcoded — enforced by a test

Extend the capability ratchet (`scripts/lib/capabilities.js`) into a strict
check that **fails** on, in playground sources: a literal `font-size`; a
hand-written `var(--uxdsl__…)`; `px` on spacing, edge or shadow
properties; a hex, `rgb()` or `hsl()` color outside theme JSON; a
hand-written `@media`; a `style={{ }}` carrying a literal (allowed: a
theme-derived value passed as a custom property, e.g. a measured width for the
resize frame); a `<button>`, `<input>`, `<textarea>` or `<pre>` outside its
one component. A short allowlist file records each remaining exception with
a one-line reason and the test counts it. Expected exceptions: literal code
*samples* shown as text (strings, not styles), and SideNav's
`@media (min-width: 1024px)`, which exists because a directive cannot be
applied from a named breakpoint — keep it as the single documented exception
(adding syntax for it is out of beta.9's scope), and say so on the page that
documents directives. `not-found`'s `@media (min-width: 600px)` becomes a
breakpoint function.

The phase-B visual comparison harness (`fixtures/playground-browser`) runs
before and after each unification step; intended visual changes are
declared, everything else must be identical. The capability matrix stays at
0 gaps and the browser walk green (no overflow, focus visible, contrast page
equal to Node).

### 8.1 Scoped palettes reach every composite (their item 1, the priority)

Done when a container that overrides `--uxdsl__palette__primary-main` shows
that color in `border(…)` presets, `@ds-surface(…)` and `@ds-button(…)`
with no project code, in a real browser. Two designs to choose between, with
a recorded decision:

- **Emit composite values at the point of use** (`border: border(1)` →
  `border: 1px solid var(--uxdsl__palette__…)` on the element), so every
  `var()` resolves where it is used. Simple and robust, but repeats values
  in the output and changes what `applyTheme` can update (a preset's width
  would no longer be one custom property).
- **Re-declare the composite custom properties wherever a palette is
  scoped**: a `scope` option (and theme field) listing selectors that carry
  their own palette, for which the theme emits the composites for
  `:root, <selector>` (the generators already take a selector; the plugin
  hard-codes `:root`). Keeps one custom property per decision and works with
  `applyTheme`; the project names its scopes.

Recommendation: the second (it fits "the theme resolves each decision for
its context", §4.2 — a scoped palette is a context), with a CSS-level test
in Chrome. Either way it is the same idea as `modes.dark`, which already
re-declares palette values under another selector. Press Craftor's
workaround (a PostCSS step re-declaring composites on
`[style*="--uxdsl__palette__"]`) must become deletable.

### 8.2 `uxdsl audit` and `uxdsl migrate --suggest` (their item 5)

Productize their `scripts/uxdsl-audit.mjs` and this plan's §7.4 check as
one command for users:

- `uxdsl audit [--check] [--update]`: counts the decisions the theme should
  own (literal colors, spacing, radii, edges, shadows, type, hand-built
  buttons, containers, focus rings) in a project's sources, honours a
  `/* uxdsl-exception: <reason> */` marker, and with `--check` fails CI when
  a count grows past a committed baseline. The playground's §7.4 check is
  then just `uxdsl audit --check` on the playground.
- `uxdsl migrate --suggest`: proposes the nearest token or role for each
  literal (sizes → the type scale, radii → `radius(n)`, edges and shadows →
  presets) without writing.
- `uxdsl doctor` (§5.1) stays the *upgrade* tool; `audit` is the
  *adoption and drift* tool. One shared scanner.

## 9. SCSS superset — every `.scss` works as `.uxdsl` (D-1, decided)

**Decided by the owner, 2026-10-09, for beta.9.** The point is adoption: a
team on SCSS renames its files from `.scss` to `.uxdsl`, everything keeps
working exactly as before, and from then on it can start using UXDSL — one
token, one component, one file at a time. The migration starts with a rename,
not a rewrite. Evidence that it works: `docs/audits/2026-10-09-sass-layer/`
(D-1).

### 9.1 Done when

- A `.scss` file renamed to `.uxdsl` compiles to the same CSS that Dart
  Sass produces for it (the same rules, selectors and declarations, in the
  same order), through every UXDSL entry point: the CLI, `compile()`, the
  Vite plugin and the webpack loader.
- The same file can then use any UXDSL construct, mixed freely with Sass:
  Sass variables, functions and math feeding `density()`, `xs()`/`md()`,
  `palette()`; `@ds-*` directives inside mixins, `@each` and nested rules.
- Authors write exactly what they write today: the canonical grammar
  (`palette(primary.main)`, `@ds-surface(contained)`) does not change.
- An error — Sass's or UXDSL's — points at the line of the file the author
  wrote.

### 9.2 The pipeline (one place, `compile()`, shared by every entry point)

1. **Protect** UXDSL's syntax so Sass passes it through: dotted
   `palette()`/`color()` arguments become opaque calls, `$var` inside
   `@ds-*(…)` becomes `#{$var}`. A real tokenizer, not regular expressions:
   strings, comments and nested parentheses are respected, and native CSS
   such as `color(display-p3 1 0 0)` or `color(from …)` is never touched.
2. **Dart Sass** (`sass`, pure JavaScript) compiles the file: `@use`,
   `@forward`, `@import`, functions, mixins, maps, math, `@extend`,
   nesting. An importer resolves `.uxdsl` files next to `.scss`, `.css` and
   `node_modules`.
3. **Restore** the protected syntax and the spacing Sass adds in
   `@ds-x (…)`.
4. **UXDSL** (the PostCSS plugin) does what it does today.

Source maps are chained through all four steps, so every `UXD_*` diagnostic
and every devtools position refers to the author's file. A Sass error becomes
a located `UXD_SASS` diagnostic carrying Sass's message; Sass deprecation
warnings are reported as warnings with their location.

### 9.3 What it replaces

- UXDSL's own SCSS subset (`src/scss-subset.ts`), its leftover-Sass guard
  and the codes that only that guard produced (`UXD_SCSS_UNSUPPORTED`,
  `UXD_NESTING_INVALID`, `UXD_INCLUDE_ARGUMENT` — retire or repurpose them
  in `DIAGNOSTIC_CATALOG`).
- `postcss-import` for `.uxdsl` imports: Sass's module system resolves them.
- Native nesting forwarded unflattened: Sass flattens nesting, as every SCSS
  user expects (`&__title` → `.card__title`). A behavior change for the
  compiled output — listed in the CHANGELOG.

### 9.4 Decisions inside it (recommendations to confirm while building)

- **Reserved names.** UXDSL's functions (`space`, `density`, `color`,
  `palette`, `radius`, `border`, `shadow`, `tone`) and the theme's
  breakpoint names: a project `@function` or `@mixin` with one of those
  names is a located error (`UXD_RESERVED_NAME`), not a silent shadow.
- **The generated entry** uses `@use` rather than `@import` (Sass
  deprecates `@import` and will remove it in Dart Sass 3).
- **Hosts that run their own Sass** (Next.js `.module.scss` through its
  `sass-loader`): those files reach UXDSL only after the host's Sass, which
  stops on `palette(primary.main)`. Document the path — rename such a file
  to `.uxdsl` and compile it through UXDSL (CLI or loader) — and,
  recommended, also accept the quoted form `palette("primary.main")` in the
  plugin, so a file the host compiles can still use tokens.
- **Speed:** measure the playground and a large real SCSS codebase before
  and after; the audit measured +33 % for Sass plus UXDSL on 300 rules.
  Budget: no more than +50 % on the playground build.

### 9.5 Tests and evidence

- The audit's 110-case SCSS matrix becomes "equal to Dart Sass": every
  Sass-only case produces Sass's output; the UXDSL and mixed cases produce
  today's UXDSL output; none is silent.
- A real, large SCSS codebase as a fixture (for example Bootstrap 5's SCSS
  source, MIT) renamed to `.uxdsl`: its compiled CSS equals Dart Sass's.
- The playground compiles to the same rules before and after the switch, and
  `story-radar` and Press Craftor build unchanged (§2).
- A diagnostic inside a file that uses `@use`, mixins and nesting points at
  the original line (source-map chaining).
- `npm audit` on a fresh `npm i -D uxdsl` stays at 0 with `sass` added.

### 9.6 Documentation and adoption

- **"From SCSS"** becomes a first-class path in the quick start and the
  README: rename, build, then adopt tokens gradually — with `uxdsl audit` and
  `uxdsl migrate --suggest` (§8.2) proposing which literals to move first.
- The language reference (§5.3) says plainly: every SCSS feature works; UXDSL
  adds its words on top; the reserved names.
- Positioning (D-10): "SCSS, plus a design-system engine" becomes a true
  claim once this ships.
